# Internal communication delivery

## Local access
Start the backend with run-local.ps1 and the frontend with npm run dev, then sign in with the retained administrator or a real assigned employee account. The local demo setup endpoint and credential manifest have been removed for the GitHub handoff. Generated demo sign-ins are disabled and their linked demo employees inactive; history is retained. Production uses existing employee accounts and its private server configuration.

## Delivered
Private conversations and typed employee groups use the existing user/employee directory. Active linked employees with Communication access can message; unlinked/inactive accounts cannot. The interface provides conversation lists, unread counts, history pagination, bounded search, replies, forwarding, edits, reactions, pins, archives, read receipts, typing, presence, group membership controls and announcement restrictions. Notifications contain sender metadata, not message contents. Device microphone recording requires browser permission and supports preview/playback; physical microphone testing remains a device check.

The responsive interface follows the supplied split-pane private chat and group references with EAC orange, vanilla, violet ink and lime accents. Communication navigation and unread badges are integrated into existing navigation. Files has a Share via Communication action. Existing attendance, payroll and timesheet business logic is unchanged.

Attachments use the existing File Management module. Existing managed files require sender sharing permission and access for every recipient; sending never silently grants existing-file access. New device attachments are encrypted managed-file containers. PDFs, images and audio can be previewed; Office attachments can be downloaded for native editing. File Management's original document editors remain separate. Existing Office originals are not converted by this module.

## Security and persistence
The additive communication package uses conversations, participants, messages, policy, audit, uploads and backups tables. See backend src/main/resources/db/V9__internal_communication.sql. Follow the project's existing migration process for deployment; local JPA schema update is not a substitute for reviewing production SQL.

Messages and new device attachment content/metadata use AES-256-GCM with per-encryption nonces and contextual authentication. Configure a persistent server-only Base64 32-byte APP_COMMUNICATION_KEY, preserve it separately from backups and never send it to the frontend. This is server-side encryption, not end-to-end encryption. Existing shared File Management originals retain their existing storage model; deployment storage volumes must provide encryption at rest.

A dedicated /communication-ws connection authenticates using the existing JWT in its first frame. Events are scoped to eligible accounts, emitted after database commit, and contain refresh metadata only. REST checks membership for all durable reads and writes. Reconnect reloads persisted state; polling provides a fallback. Expired/revoked users cannot continue receiving events. Existing WebSocket endpoints remain in place.

ADMIN accounts can manage policies, backups, recovery, groups and audit logs directly. Non-admin accounts can be assigned individual enabled COMMUNICATION_POLICY_MANAGE, COMMUNICATION_RECOVERY_MANAGE, COMMUNICATION_BACKUP_MANAGE or COMMUNICATION_GROUP_MANAGE permissions through existing endpoint management, by user or role. Each assignment permits only that action and its matching administration page. Disabling or removing the assignment revokes access. Unassigned employees cannot use management controls. Conversation review and export are restricted to enabled ROLE_ADMIN accounts. ADMIN can review employee conversations without additional communication permission assignments. Ordinary employee accounts cannot review or export other conversations, even if review permissions or page access are accidentally assigned. Review reasons and audit records remain required. Review requires a reason; privileged requests and outcomes are audited without message contents. An optional explicit self-link flow lets an unlinked admin confirm an existing employee with the same unique email; it does not create employees or change the account role.

Deletion defaults disabled. If enabled, messages/conversations are recoverably soft deleted until their retention deadline. Recovery requires explicit grants and a reason. No automatic irreversible purge has been introduced.

## Backups and limits
Encrypted communication backups include communication rows and referenced managed-file versions, checksums and grants. Verification checks integrity; restore requires a preview confirmation and restores missing records without overwriting existing messages, policies or permissions. Scheduled backups begin after startup initialization. Protect the backup directory and key separately; configure offsite replication operationally. Backup retention is recorded, but physical expiration purging is not automatic.

Current safeguards include 100 conversations per list, 50 messages per history/export page, bounded 500-message search batches with a continuation cursor, 100,000 messages per backup, 100 MB attachment content per backup and 180 MB manifest cap. Upload signatures, paths and archive expansion are checked; no antivirus engine is configured. Voice duration is client/declaration constrained rather than independently decoded on the server. Presence/rate-limit maps are instance-local; clustered deployment needs shared coordination. Use TLS with APP_COMMUNICATION_REQUIRE_TLS=true in deployment and configure allowed frontend origins. Verify account page grants, storage access, key persistence, database migrations and backup restoration in staging.

## Integration map
Frontend: src/pages/Communication contains the API client, provider, private/group pages, administration pages, composer, voice recorder, attachment cards, managed-file picker and Files sharing dialog. App.jsx adds routes; mainSidebar.jsx adds navigation/unread state; the central dashboard adds the module entry; FileExplorer.jsx adds sharing.

Backend: the communication package contains entities, repositories, access checks, encryption, service/controller, audit, presence/events, authenticated WebSocket transport, scoped transport security, backup service and the opt-in local demo setup controller. files/CommunicationFilesBridge.java integrates existing file operations and ACLs. Configuration adds communication properties and run-local.ps1 accepts the local key and demo flag.

Employee routes: /communication and /communication/groups. Privileged routes: /admin/communications, /admin/communication-settings, and /admin/communications/{groups,recovery,backups,audit}. APIs are under /api/communication: me, directory, conversations/direct, groups, conversation messages/receipts/typing/attachments/preferences/search, message actions and admin review/policy/recovery/backups/audit. File access is always checked server-side.

## Sign-in notifications and employee directory
The global Communication provider retrieves recipient-scoped persisted unread previews after authentication. A dismissible banner shows sender, unread count and a text preview (up to 160 characters); each entry opens its exact conversation. The same banner handles new incoming messages while another conversation or module is open. Opening a chat uses the existing read receipt behavior. Dismissing the banner does not mark messages read; unread messages return on the next sign-in. Muted and archived threads are excluded from banners. Up to ten unread conversations are shown, with the existing unread badge retained. Banner state and pending requests are isolated by authenticated session, cleared on account changes, and hidden on login screens. Desktop notifications remain opt-in.

The default desktop Communication view displays the employee directory, and a persistent Open employee directory button is available beside the conversation list. The direct/group pickers share the same component. They call the existing GET /api/employee endpoint with view=communication and an optional search query. This view returns employee names, employee codes, department, linked user ID and availability only; it never returns salary, identity, bank or personal contact fields. The existing full employee API response remains unchanged for other views. All employee records are listed, including self and unavailable accounts labelled with their status. Only eligible linked accounts can be selected for messaging; no chat is created until a colleague is clicked. Existing membership, page and account checks still protect sends.
